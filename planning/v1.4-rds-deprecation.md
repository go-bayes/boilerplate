# v1.4 RDS deprecation and workflow hardening

## Scope of this plan

This document tracks the work required to ship `1.4.0`, to finish hardening the
package against automated/agentic misuse, and to remove RDS entirely in a later
major release. Changes already made on the `v1.4-security-json-default` branch
are listed first so that the remaining work is visible at a glance.

## Already done on the branch

* Flipped the default `format` to `"json"` in `boilerplate_export()` and the
  internal `write_boilerplate_db()` helper.
* Flipped the default database filename produced by `get_db_file_path()` to
  `*_db.json`.
* Added `warn_rds_deprecated()` helper and called it from `boilerplate_save()`
  and `boilerplate_export()` whenever `format` is `"rds"` or `"both"`.
  `boilerplate_init()` inherits the warning through delegation.
* Updated roxygen examples in `boilerplate_init()`, `boilerplate_save()`, and
  `boilerplate_export()` so the canonical demonstrations use JSON.
* Migrated two incidental-RDS tests (`test-generate-text.R`,
  `test-vignette-internals.R`) to JSON. Migration-tests and
  version-management tests still use RDS on purpose.
* Updated `DESCRIPTION`'s description field and bumped the dev version to
  `1.3.0.9002`.
* Added a `1.3.0.9002` section to `NEWS.md` documenting the change and its
  motivation.
* Drafted a `1.4.0` section at the top of `cran-comments.md`.

## Documentation work still needed before shipping 1.4.0

The list below is in recommended order. Each item is expected to be a small,
contained change.

* Replace the "JSON Default Format" bullet's "with RDS backward compatibility"
  language with a brief sentence noting that RDS writing is deprecated and
  that the migration helpers remain available.
* Remove or rewrite sections that currently walk users through saving RDS
  (for example the example at README line 1355 that shows
  `boilerplate_export(unified_db, output_file = "backup_before_cleaning.rds")`).

## Security hardening deferred to a 1.4.x follow-up branch

The following items were identified in the security-review scoping pass.
None block `1.4.0`, but each is small enough to land in a focused follow-up.

1. **Symlink-safe copies.** Five `file.copy()` sites
   (`bibliography-support.R:13`, `:191`; `import-export-functions.R:183`;
   `migration-utilities.R:130`, and one in `boilerplate_restore_backup`).
   Pass `copy.mode = FALSE` and verify that the resolved target remains
   inside the declared project or cache root via `normalizePath()`.
2. **URL-scheme restrictions for bibliography downloads.**
   `boilerplate_update_bibliography()` at `bibliography-support.R:106`
   should accept only `https://` URLs by default, with `file://` as an
   explicit opt-in. Cache filenames should be derived with `basename()`
   and re-resolved under the cache directory.
3. **Download size cap.** `utils::download.file()` can allocate
   unboundedly when pointed at a hostile resource. Either apply a size
   limit or use `curl::curl_download()` with a timeout and a `max-filesize`
   header.
4. **Trusted-root gate for `readRDS()` in `boilerplate_import()`.**
   For the deprecation window, refuse to read `.rds` files that lie
   outside the declared project root unless the caller passes
   `allow_rds = TRUE`. Pair the gate with a one-line message pointing at
   the migration helper.
5. **JSON size and depth cap.** `jsonlite::read_json()` on a very large
   or deeply nested file can exhaust memory or stack. Set a conservative
   upper bound when parsing untrusted input.

## v2.0 roadmap (full RDS removal)

* Remove `readRDS()` and `saveRDS()` calls from everywhere except
  `boilerplate_migrate_to_json()` and `boilerplate_rds_to_json()`.
* Narrow the `boilerplate_import()` extension check to `\\.json$`.
* Remove `format = "rds"` and `format = "both"` from the choices accepted
  by `boilerplate_save()`, `boilerplate_export()`, and `boilerplate_init()`.
* Drop the `warn_rds_deprecated()` helper.
* Migration tooling stays as a one-way door; users with legacy databases
  still have a path off.

## Split of the four "mixed" boundary functions (deferred)

`boilerplate_batch_edit()`, `boilerplate_batch_edit_multi()`,
`boilerplate_batch_clean()`, and `boilerplate_copy_from_project()` each
accept either a file path or an in-memory database. This dual behaviour
is the only place the trust boundary is ambiguous, because an agent
cannot tell from the signature whether a call will do I/O. Splitting each
into `_on_db()` (interior) and `_on_file()` (boundary) pairs is the main
breaking change to consider for `2.0`. It is not needed before agentic
adoption becomes common.
