# v1.4 RDS deprecation and workflow hardening

Date updated: 2026-07-09

This document records the current `1.4.0` release policy. Earlier drafts on this branch described a warn-on-write transition with full removal deferred to `2.0`; the implementation now takes the safer route for `1.4.0`.

## Current release policy

`1.4.0` removes RDS writing from package APIs. `boilerplate_save()`, `boilerplate_export()`, `boilerplate_init()`, and the internal `write_boilerplate_db()` helper all error when callers request `format = "rds"` or `format = "both"`. `boilerplate_export(output_file = "*.rds")` also errors before creating directories or files.

RDS reading remains available only as a legacy bridge. `boilerplate_import()`, `boilerplate_rds_to_json()`, `boilerplate_migrate_to_json()`, and `compare_rds_json()` can still read trusted legacy RDS files. Every RDS read goes through `read_rds_database()` and emits a real R warning before `readRDS()` deserialises the file. `quiet = TRUE` does not suppress that safety warning.

When JSON and RDS versions of the same database both exist, import prefers JSON. If the ignored RDS file is newer than the JSON file, import emits a warning so users do not silently load stale JSON in a mixed legacy directory.

`boilerplate_batch_edit()` loads JSON file paths only. Legacy RDS files must first pass through `boilerplate_import()` or `boilerplate_migrate_to_json()`, so every RDS read funnels through the warning path.

## Follow-up hardening for 1.4.x

These items do not block `1.4.0`.

1. Add a trusted-root or explicit-consent gate for RDS reads in `boilerplate_import()`.
2. Reconcile the two backup conventions: `create_db_backup()` writes `*.json.<timestamp>.bak`, but `boilerplate_import()` rejects `.bak` extensions, so `boilerplate_restore_backup()` can only restore `_backup_*.json`/`.rds` named files. Pre-existing behaviour, found during the 1.4.0 review.
3. Make copy and backup operations symlink-safe.
4. Restrict bibliography downloads to safe URL schemes.
5. Add download size/time limits.
6. Add conservative size/depth limits for JSON parsing.

## Trust-boundary split for 2.0

`boilerplate_batch_edit()`, `boilerplate_batch_edit_multi()`, `boilerplate_batch_clean()`, and `boilerplate_copy_from_project()` accept either an in-memory database or an argument that triggers file I/O, so a caller — human or agent — cannot tell from the signature whether a call touches the file system. Splitting each into an `_on_db()` pair (pure, in-memory) and an `_on_file()` pair (explicit boundary, does I/O) removes the ambiguity at the type level rather than by convention. `1.4.0` narrowed `boilerplate_batch_edit()` file paths to JSON; the split remains the structural fix and is the main breaking change to schedule for `2.0`.

## Context packs (post-1.4.0 feature)

Small, auditable exports from the JSON database intended for assistant sessions: the exact selected entries, their source paths, the template variables they use, and an omission report stating what was left out of the pack. A fresh assistant session loads the pack; a compacted or summarised conversation history is never the source of record. Design constraints:

- A pack is plain JSON, produced by an exported function (working name `boilerplate_export_pack()`), and is reproducible from the database plus the selection spec.
- The omission report is mandatory, so a reader can tell selection from absence.
- Ship with its own vignette that documents selective sharing — packs and `boilerplate_export(select_elements = ...)` — as the recommended alternative to passing whole databases between collaborators or sessions.

## Longer-term RDS removal

After a transition period, remove RDS reading from general import paths. Keep a clearly named migration-only path if users still need a one-way conversion tool for old databases.
